# 테스트 자동화 방법론 (test-automation)

디렉토리 전체를 검사해 서비스별 **통합 테스트를 생성·실행**하고, 그 과정에서 드러나는 **결함과 위험**을
근거 기반으로 정리하는 방법론입니다.

## 0. 분석 철학

- **통합 테스트가 목표**: 개별 함수의 단위 동작이 아니라, 구성요소가 함께 동작할 때의 정확성을 검증합니다.
  대표 통합 경계: API 핸들러 ↔ 서비스 로직 ↔ 데이터 계층, 서비스 간 호출, 외부 API/메시지 큐 연동.
- **생성 + 실행**: 테스트를 만들고 실제로 돌려 통과/실패를 확인합니다.
- **정직성**: 통합 테스트는 환경 의존성이 큽니다. 실행이 불가능하면 통과시키려 하지 말고,
  "무엇이 없어서 못 돌렸는지"를 레포트에 남기고 정적 위험 분석으로 보완합니다.
- **격리/결정성**: 테스트는 서로 독립적이고 반복 실행해도 같은 결과(결정적)여야 합니다. 플래키 테스트는 만들지 않습니다.
- **부수효과 금지**: 실서버/실데이터를 건드리지 않습니다. 테스트 더블, 인메모리/임시 DB, testcontainers를 사용합니다.

## 1. 서비스/통합 지점 인벤토리

테스트 설계 전 다음을 파악합니다.

1. 파일 트리, 언어 구성, 의존성 매니페스트 (`requirements.txt`/`pyproject.toml`, `package.json`, `pom.xml`/`build.gradle`)
2. 서비스/모듈 경계와 진입점 (라우트, 핸들러, 메인, 컨슈머, 스케줄러)
3. **통합 지점(seam)**: DB 쿼리/ORM, 외부 HTTP 호출, 메시지 큐, 캐시, 파일/네트워크 I/O, 서비스 간 호출
4. 데이터 흐름: 입력 → 처리 → 영속화/응답 경로
5. 기존 테스트 유무와 테스트 프레임워크
6. 설정/환경변수, 인증 방식

규모가 크면 위험·중요도 높은 경로부터 우선합니다: 핵심 비즈니스 트랜잭션 → 외부 연동 → 데이터 영속화 → 인증/인가.

## 2. 테스트 환경 준비 (full / run-only)

통합 테스트는 환경이 핵심입니다.

- **의존성 설치**: 언어별 설치 (`pip install -r ...`, `npm ci`, `mvn -q test-compile` 등).
- **외부 의존성 처리** (우선순위 순):
  1. testcontainers 등으로 실제와 유사한 일회용 컨테이너(DB/큐) 사용
  2. 인메모리/임시 DB (SQLite, H2) 또는 로컬 테스트 인스턴스
  3. 테스트 더블(목/스텁/페이크) — 네트워크 외부 API 등 제어 불가 대상
- **픽스처/시드 데이터**: 각 테스트가 독립적으로 쓰도록 setup/teardown에서 준비·정리.
- **환경변수**: 테스트 전용 설정을 분리(.env.test 등). 실 자격증명 사용 금지.
- 환경 구성이 불가능하면 누락 요소(예: "PostgreSQL 미기동", "Docker 미설치")를 기록하고 generate-only로 폴백.

## 3. 언어별 통합 테스트 생성 가이드 (full / generate-only)

### Python (pytest)
- `conftest.py`에 공용 픽스처(테스트 DB 세션, 앱 클라이언트 등) 정의.
- HTTP API: `httpx`/`requests` 또는 프레임워크 테스트 클라이언트(FastAPI `TestClient`, Flask `test_client`).
- 비동기: `pytest-asyncio`. DB: 트랜잭션 롤백 픽스처 또는 testcontainers.
- 파일 배치: `tests/integration/test_<서비스>.py`.

### JavaScript / TypeScript (Jest/Vitest, Playwright)
- HTTP API 통합: `supertest`로 앱 인스턴스에 요청. setup/teardown은 `beforeAll/afterAll`.
- E2E/외부 경유 API: Playwright (`request` 컨텍스트 또는 브라우저 컨텍스트).
- DB/외부: 테스트 컨테이너 또는 인메모리 대체. 파일 배치: `tests/integration/<서비스>.spec.ts`.

### Java / Kotlin (JUnit 5)
- Spring 환경: `@SpringBootTest` + `MockMvc`/`WebTestClient`로 통합 검증.
- DB/큐: Testcontainers(`@Testcontainers`, `@Container`). API 검증: RestAssured.
- 파일 배치: `src/test/java/.../<서비스>IntegrationTest.java`.

### 범용(그 외 언어)
- 언어 표준 테스트 러너를 감지해 동일 원칙으로 작성.
- 자동 생성이 어려우면, 통합 시나리오(전제→입력→기대 결과)를 표 형태로 문서화해 레포트에 포함.

## 4. 테스트 설계 원칙

각 통합 지점마다 다음 시나리오를 고려합니다.

- **행복 경로**: 정상 입력 → 기대 응답 + 올바른 부수효과(DB 반영 등) 검증.
- **경계/예외 입력**: 빈 값, 한계값, 잘못된 형식, 권한 없음.
- **통합 실패 시나리오**: 의존성 실패(DB 다운, 외부 API 타임아웃/에러), 부분 실패, 트랜잭션 롤백, 재시도/멱등성.
- **데이터 무결성**: 동시 요청, 유니크 제약, 일관성.
- 단언(assertion)은 응답뿐 아니라 **상태 변화**(저장/갱신/삭제 결과)까지 확인합니다.

## 5. 테스트 실행 (full / run-only)

`tools/run_tests.sh <대상경로>`가 언어를 감지해 실행하고 결과를 `reports/.tests/`에 모읍니다.

- 결과 집계: 통과/실패/에러 수, 실패 케이스별 원인(스택트레이스 요약).
- 가능하면 커버리지(통합 관점)도 수집(예: pytest-cov, jest --coverage).
- 실행 불가 시: 러너/의존성 부재 사유를 기록하고 6단계 정적 위험 분석을 강화.

## 6. 결함(Defect) / 위험(Risk) 분석

- **결함(Defect)**: 실패한 테스트 → 재현 조건, 기대값 vs 실제값, 추정 원인(`파일:라인`)을 기술.
- **위험(Risk)**: 테스트로 확정되진 않았으나 잠재적 문제.
  - 미검증 통합 경로(테스트가 닿지 않는 분기/에러 핸들러)
  - 경계값/널 처리 미흡, 동시성·레이스 가능성, 트랜잭션 경계 모호
  - 외부 의존성 실패 시 처리 부재(타임아웃/재시도/서킷브레이커 없음)
  - 계약 불일치(스키마/응답 형식이 소비자 기대와 다름)
  - 플래키 가능성(시간/순서/외부 상태 의존)
- CLAUDE.md 기준으로 Blocker/Critical/Major/Minor/Risk 등급 부여.

## 7. 레포트 작성

`templates/report_template.md` 구조를 따릅니다. 핵심 섹션:
요약 → 서비스/통합 지점 인벤토리 → 생성 테스트 목록 → 실행 결과 → 결함 → 잠재 위험 → 커버리지 공백 → 우선 개선 로드맵 → 재현/실행 방법.

각 결함/위험은 위치(`파일:라인` 또는 테스트명), 등급, 설명, 재현/근거, 권장 조치를 포함합니다.

## 8. 출력물 생성

1. Markdown: `reports/<KST타임스탬프>_qa_report.md`
   - 타임스탬프: `TZ=Asia/Seoul date '+%y%m%d%H%M'` (윈도우: `Get-Date -Format 'yyMMddHHmm'`)
2. HTML: 빌더 실행 (운영체제에 맞는 파이썬 명령)
   - 윈도우: `python tools/build_report.py reports/<...>.md`
   - macOS/Linux: `python3 tools/build_report.py reports/<...>.md`
   - `.html` 생성 여부를 반드시 확인. 없으면 `python -m pip install markdown` 후 재실행.
3. PDF: 자동 생성하지 않음. HTML을 브라우저에서 Ctrl+P로 저장하도록 안내.

## 9. 품질 자가 점검 (레포트 제출 전)

- [ ] 통합 지점을 빠짐없이 식별했는가?
- [ ] 생성한 테스트가 격리·결정적이며 부수효과가 없는가?
- [ ] 테스트를 실제로 실행했는가? (불가 시 사유를 명시했는가?)
- [ ] 실패를 통과로 위장하지 않았는가?
- [ ] 각 결함에 재현 조건과 추정 원인이 있는가?
- [ ] 각 위험에 근거와 권장 조치가 있는가?
- [ ] 재현/실행 방법을 적어, 사용자가 직접 돌릴 수 있는가?
- [ ] 한글로 작성했는가?
