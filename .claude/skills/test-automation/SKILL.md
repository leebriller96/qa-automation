# 테스트 자동화 방법론 (test-automation)

디렉토리 전체를 검사해 서비스별 **통합 테스트를 생성·실행**하고, 그 과정에서 드러나는 **결함과 위험**을
근거 기반으로 정리하는 방법론입니다. `/qa` 명령의 상세 절차는 이 문서 한 곳에서 관리합니다.

## 0. 분석 철학

- **통합 테스트가 목표**: 개별 함수의 단위 동작이 아니라, 구성요소가 함께 동작할 때의 정확성을 검증합니다.
  대표 통합 경계: API 핸들러 ↔ 서비스 로직 ↔ 데이터 계층, 서비스 간 호출, 외부 API/메시지 큐 연동.
- **생성 + 실행**: 테스트를 만들고 실제로 돌려 통과/실패를 확인합니다.
- **정직성**: 통합 테스트는 환경 의존성이 큽니다. 실행이 불가능하면 통과시키려 하지 말고,
  "무엇이 없어서 못 돌렸는지"를 레포트에 남기고 정적 위험 분석으로 보완합니다.
- **수치는 도구에서**: 통과/실패/에러 수는 `reports/.tests/summary.json`에서 가져옵니다. 직접 세거나 추정하지 않습니다.
- **실패 ≠ 결함**: 실패한 테스트는 반드시 원인 분류(§6)를 거친 뒤에만 결함으로 보고합니다.
- **격리/결정성**: 테스트는 서로 독립적이고 반복 실행해도 같은 결과여야 합니다. 플래키 테스트는 만들지 않습니다.
- **부수효과 금지**: 실서버/실데이터를 건드리지 않습니다. 테스트 더블, 인메모리/임시 DB, testcontainers를 사용합니다.

## 0-1. 안전 규칙

- **임의 코드 실행 주의**: `npm test`, `mvn test`, `pytest` 등은 `input/`의 코드(테스트, postinstall 스크립트, conftest 등)를
  **그대로 실행**합니다. 출처가 불분명한 코드라면 실행 전에 사용자에게 알리고, 요청이 있으면 `generate-only`로 진행합니다.
- **시크릿 보호**: `input/`의 `.env`, 키 파일, 토큰, 접속 문자열을 레포트·테스트 코드·채팅에 **복사하지 않습니다**.
  인용이 필요하면 `DB_PASSWORD=***`처럼 마스킹합니다. 노출된 자격증명 자체는 Risk로 보고합니다.
- **네트워크 격리 전제**: 테스트가 외부 실서비스(결제, 메일, 서드파티 API)에 실제 요청을 보내지 않도록 목/스텁으로 차단합니다.

## 1. 분석 대상 확보

- `/qa [mode] [path]`의 `path`가 있으면 그 경로, 없으면 `input/` 전체가 대상입니다.
- 사용자가 코드를 채팅에 붙여넣었다면 `input/pasted_<KST타임스탬프>/`에 파일로 저장한 뒤 그 경로를 대상으로 합니다.
  (이렇게 해야 생성 테스트의 저장 위치와 러너 실행 경로가 생깁니다.)
- 대상이 없으면 "input/에 서비스 코드를 넣거나 코드를 붙여넣어 주세요"라고 안내하고 중단합니다.

## 2. 서비스/통합 지점 인벤토리

테스트 설계 전 다음을 파악합니다.

1. 파일 트리, 언어 구성, 의존성 매니페스트 (`requirements.txt`/`pyproject.toml`, `package.json`, `pom.xml`/`build.gradle`, `go.mod` 등)
2. 서비스/모듈 경계와 진입점 (라우트, 핸들러, 메인, 컨슈머, 스케줄러)
3. **통합 지점(seam)**: DB 쿼리/ORM, 외부 HTTP 호출, 메시지 큐, 캐시, 파일/네트워크 I/O, 서비스 간 호출
4. 데이터 흐름: 입력 → 처리 → 영속화/응답 경로
5. 기존 테스트 유무와 테스트 프레임워크
6. 설정/환경변수, 인증 방식 (값은 보지 않고 **키 이름만** 기록)

규모가 크면 위험·중요도 높은 경로부터 우선합니다: 핵심 비즈니스 트랜잭션 → 외부 연동 → 데이터 영속화 → 인증/인가.
분석하지 않기로 한 영역은 레포트의 "분석 범위 / 제외 / 가정"에 반드시 적습니다.

## 3. 테스트 환경 준비 (full / run-only)

통합 테스트는 환경이 핵심입니다.

- **의존성 설치**: 언어별 설치 (`pip install -r ...`, `npm ci`, `mvn -q test-compile` 등). 서비스 디렉토리 안에서 수행합니다.
- **외부 의존성 처리** (우선순위 순):
  1. testcontainers 등으로 실제와 유사한 일회용 컨테이너(DB/큐) 사용
  2. 인메모리/임시 DB (SQLite, H2) 또는 로컬 테스트 인스턴스
  3. 테스트 더블(목/스텁/페이크) — 네트워크 외부 API 등 제어 불가 대상
- **픽스처/시드 데이터**: 각 테스트가 독립적으로 쓰도록 setup/teardown에서 준비·정리.
- **환경변수**: 테스트 전용 설정을 분리(.env.test 등). 실 자격증명 사용 금지.
- 환경 구성이 불가능하면 누락 요소(예: "PostgreSQL 미기동", "Docker 미설치")를 기록하고 `generate-only`로 폴백합니다.

## 4. 통합 테스트 생성 (full / generate-only)

### 설계 원칙 — 각 통합 지점마다 다음 시나리오를 고려

- **행복 경로**: 정상 입력 → 기대 응답 + 올바른 부수효과(DB 반영 등) 검증.
- **경계/예외 입력**: 빈 값, 한계값, 잘못된 형식, 권한 없음.
- **통합 실패 시나리오**: 의존성 실패(DB 다운, 외부 API 타임아웃/에러), 부분 실패, 트랜잭션 롤백, 재시도/멱등성.
- **데이터 무결성**: 동시 요청, 유니크 제약, 일관성.
- 단언(assertion)은 응답뿐 아니라 **상태 변화**(저장/갱신/삭제 결과)까지 확인합니다.
- 테스트 함수명은 `test_<시나리오>_<기대결과>`처럼 의도가 드러나게 짓고, 레포트의 테스트 ID(T-001)와 함수명을 함께 기록합니다.

### 언어별 가이드 (스니펫: `references/fixture-patterns.md`)

- **Python (pytest)**: `conftest.py`에 공용 픽스처(테스트 DB 세션, 앱 클라이언트). HTTP는 프레임워크 테스트 클라이언트
  (FastAPI `TestClient`, Flask `test_client`) 또는 `httpx`. 비동기는 `pytest-asyncio`. 배치: `tests/integration/test_<서비스>.py`.
- **JavaScript / TypeScript (Jest/Vitest, Playwright)**: `supertest`로 앱 인스턴스에 요청, `beforeAll/afterAll`로 setup/teardown.
  E2E는 Playwright. 배치: `tests/integration/<서비스>.spec.ts`.
- **Java / Kotlin (JUnit 5)**: `@SpringBootTest` + `MockMvc`/`WebTestClient`, DB/큐는 Testcontainers. 배치: `src/test/java/.../<서비스>IntegrationTest.java`.
- **Go**: `net/http/httptest` + 표준 `testing`, DB는 testcontainers-go 또는 SQLite. 배치: `<pkg>/*_integration_test.go`.
- **범용**: 언어 표준 러너를 감지해 동일 원칙으로 작성. 자동 생성이 어려우면 통합 시나리오(전제→입력→기대 결과)를 표로 문서화해 레포트에 포함.

생성한 테스트는 대상 서비스의 관례 위치(없으면 `<서비스>/tests/integration/`)에 저장합니다.

## 5. 테스트 실행 (full / run-only)

```bash
tools/run_tests.sh <대상경로> [--timeout 초]     # Windows 는 Git Bash 에서 실행
```

- 대상 아래의 프로젝트를 **재귀 탐색**(`node_modules`/`.venv`/`build` 등 제외)해 언어별 러너를 실행하고
  `reports/.tests/`에 `runs.tsv`, 러너별 결과 파일, `summary.json`/`summary.md`/`cases.json`을 만듭니다.
- **full 모드는 기존 테스트 + 생성 테스트를 모두 실행**합니다. 기존 테스트의 실패도 결함 근거가 됩니다.
- `summary.md`의 수치와 실패 목록을 레포트 4절에 그대로 옮깁니다. `runs.tsv`의 status가 `runner-missing`/`deps-missing`/
  `no-test-script`/`timeout`이면 그 사실을 실행 환경 항목에 적습니다.
- 러너가 하나도 실행되지 않으면(종료 코드 2) 사유를 기록하고 `generate-only`로 폴백합니다.
- 프로파일 조건부 테스트(예: Gradle `-Pmysql`)는 `GRADLE_ARGS`/`MAVEN_ARGS` 로 한 번 더 실행하고 `--keep` 으로 결과를 합칩니다.
  환경 기동이 필요한 스위트(통합 테스트)는 `QA_PRE_RUN`/`QA_POST_RUN` 으로 기동·정리 스크립트를 걸거나, 불가하면 `QA_EXCLUDE_DIRS` 로 제외하고 "환경 문제" 로 기록합니다.
- Windows(Git Bash)에서는 `runs.tsv` 의 result_path glob 이 네이티브 경로로 변환되며 `*`/`**` 가 보존됩니다(cygpath 가 glob 을 지우는 문제는 수정됨). 집계가 0건이면 `runs.tsv` 의 result_path 를 먼저 확인합니다.
- 가능하면 커버리지(통합 관점)도 수집합니다(예: `pytest --cov`, `jest --coverage`).

## 6. 실패 원인 분류 (triage) — 결함 확정 전 필수

실패/에러 테스트 각각을 다음 중 하나로 분류합니다.

| 분류 | 판단 기준 | 처리 |
|------|-----------|------|
| **서비스 결함** | 테스트의 전제·기대값이 코드/명세상 타당한데 서비스가 다르게 동작 | Defect로 보고 (§7) |
| **테스트 결함** | 테스트가 API/스키마를 잘못 가정, 픽스처 오류, 잘못된 기대값 | 테스트를 수정하고 **재실행**. 수정 이력은 레포트에 한 줄로 남김 |
| **환경 문제** | 의존성 미설치, 포트/DB 미기동, 권한, 타임아웃 | 커버리지 공백 + 실행 불가 사유로 기록. 결함 아님 |

- **재실행 규칙**: 서비스 결함으로 판단한 테스트는 최소 1회 더 실행합니다(`tools/run_tests.sh --keep`으로 결과 보존).
  결과가 바뀌면 결함이 아니라 **플래키(Risk)** 로 분류하고 시간/순서/외부 상태 의존 원인을 적습니다.
- 분류 근거(에러 메시지, 관련 `파일:라인`)를 결함 항목의 "근거"에 남깁니다.
- 판단이 어려우면 "결함 추정(미확정)"으로 표기하고 확정에 필요한 정보를 적습니다. 확신 없는 항목을 확정처럼 쓰지 않습니다.

## 7. 결함(Defect) / 위험(Risk) 분석

- **결함(Defect)**: §6에서 서비스 결함으로 확정된 것 → 재현 조건, 기대값 vs 실제값, 추정 원인(`파일:라인`)을 기술.
- **위험(Risk)**: 테스트로 확정되진 않았으나 잠재적 문제.
  - 미검증 통합 경로(테스트가 닿지 않는 분기/에러 핸들러)
  - 경계값/널 처리 미흡, 동시성·레이스 가능성, 트랜잭션 경계 모호
  - 외부 의존성 실패 시 처리 부재(타임아웃/재시도/서킷브레이커 없음)
  - 계약 불일치(스키마/응답 형식이 소비자 기대와 다름)
  - 플래키 가능성(시간/순서/외부 상태 의존), 노출된 자격증명
- CLAUDE.md 기준으로 Blocker/Critical/Major/Minor/Risk 등급 부여.

## 8. 레포트 작성

`templates/report_template.md` 구조를 따릅니다. 핵심 섹션:
요약 → 분석 범위/제외/가정 → 서비스/통합 지점 인벤토리 → 생성 테스트 목록 → 실행 결과(+원인 분류) → 결함 → 잠재 위험 → 커버리지 공백 → 우선 개선 로드맵 → 재현/실행 방법.

각 결함/위험은 위치(`파일:라인` 또는 테스트명), 등급, 설명, 재현/근거, 권장 조치를 포함합니다.

## 9. 출력물 생성

1. **타임스탬프(KST)**: `TZ=Asia/Seoul date '+%y%m%d%H%M'` (PowerShell: `Get-Date -Format 'yyMMddHHmm'`)
2. **Markdown**: `reports/<타임스탬프>_qa_report.md`
3. **HTML**: `python tools/build_report.py reports/<...>.md` (macOS/Linux는 `python3`)
   - `.html` 생성 여부를 반드시 확인. `markdown` 미설치 에러면 `python -m pip install -r tools/requirements.txt` 후 재실행.
4. **PDF**: 자동 생성하지 않음. HTML을 브라우저에서 Ctrl+P로 저장하도록 안내.
5. **생성 테스트 회수 안내**: `input/`은 git 무시 대상이므로, 생성한 테스트 파일 목록을 레포트 3절에 적고
   사용자가 원본 저장소로 복사해야 한다는 점을 요약 보고에 포함합니다.

## 10. 요약 보고 (채팅)

두괄식으로: 서비스 수, 생성/실행 테스트 수(`summary.json` 기준), 통과·실패·에러, 확정 결함 수(+미확정 수), Top 3 우선 조치,
레포트 경로(MD/HTML), 생성 테스트 위치와 회수 방법.

## 11. 품질 자가 점검 (레포트 제출 전)

- [ ] 통합 지점을 빠짐없이 식별했고, 보지 않은 영역을 "범위/제외/가정"에 적었는가?
- [ ] 생성한 테스트가 격리·결정적이며 부수효과가 없는가?
- [ ] 테스트를 실제로 실행했는가? 수치를 `summary.json`에서 가져왔는가? (불가 시 사유를 명시했는가?)
- [ ] 실패마다 원인 분류(서비스/테스트/환경)를 했고, 테스트 결함은 수정 후 재실행했는가?
- [ ] 서비스 결함은 재실행으로 재현을 확인했는가?
- [ ] 실패를 통과로 위장하거나, 검증을 약화시키지 않았는가?
- [ ] 각 결함에 재현 조건과 추정 원인(`파일:라인`)이 있는가? 각 위험에 근거와 권장 조치가 있는가?
